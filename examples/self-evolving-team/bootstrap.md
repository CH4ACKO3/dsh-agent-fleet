# 持续改进 dsh-agent-fleet

在当前隔离仓库中持续阅读、理解并改进 dsh-agent-fleet 自身源码，提升真实可靠性、协作收益、迭代速度、代码质量与用户体验。每位成员先按自己的职责查看相关源码、测试、历史提交和运行证据，再提出或执行改进；主动识别重复逻辑、职责混杂、过深分支、脆弱状态耦合、过期路径等有证据的 code smell，不要只讨论流程。发现的问题不能只临时绕过：写入团队文件 `evidence/evolution-backlog.md`，记录证据、影响、建议 owner、适合本代修复还是后代接手，以及下一步入口。每一代只选择一个有明确证据的主改进主题，并通过测试与独立审查证明它没有破坏长任务连续性、必要唤醒、定向回复和空闲恢复。

长期产品面包括 agent team、自动研究、循环工程和 harness：产品负责人可以统筹新特性、第三方兼容或子插件；界面工程师专注人类视角的 Fleet UI/UX 与信息可见性，并使用仓库内 `.agents/skills/impeccable`；协作可靠性工程师同时审计工具、提示词与框架语义；架构师和核心工程师可合作进行有边界的深层改进；质量工程师独立维护质量与审查；平台工程师维护跨代工具、依赖、脚手架和 Patchouli 记忆继承。Patchouli 的跨代可用性是平台、质量、协作可靠性和架构的交叉责任：分别负责复制机制、候选检索验收、召回收益/成本和权威边界。团队还应逐代研究“先让成员讨论、再由助理形成任务图”的产品方向，但在证明新的生命周期能处理无人工作、异常恢复和交接连续性之前，不直接移除当前可靠入口。

这是一个持续加速的代际任务，不以完成单次修改作为整个目标结束。当前代完成一项改进后，应构建并观察一个隔离候选代；候选代自证、上一代复核并晋升后，还必须由新稳定代成功启动并验收自己的下一代，才能证明代际链路可继续。先打扫已经确认的 bug 和失败现场，再按风险与收益把结构性债务纳入后续代次；大型文件或深层耦合不是规避重构的理由，可以分代重构，但必须从发现当代就进入日程，不能让每代重新发现、再次绕过。每一代还应顺手消除一个已经观察到的交接摩擦，例如让入口、关键状态、失败证据、验证命令和下一步更容易被后代找到；也可以尝试修改下一代团队的 bootstrap、角色职责或协作提示词来提升效率，但必须说明依据并由候选代验证效果，不要为尚未发生的问题增加新流程。成员发现自己或他人的工作方式反复造成低效、遗漏或错误时，应及时给出具体证据并讨论后代如何调整；交接时优先思考如何改进下一代中同角色的提示词、入口和工具。

## 代际规则

- 第一项动作必须读取 `generation-control info` 与 `.self-evolve/generation.json`，按角色进入不同路径。`candidate` 在晋升前只验证父代交付：构建、相关测试、团队启动、协作链和跨代记忆；不得选择新的改进主题、修改 backlog 业务项、启动下一候选或执行完整稳定代工作流。验证通过后由本代平台工程师提交 `ready` 并等待父代决定；只有收到 `generation.promoted`、确认自己成为 `stable` 后，才开始下一轮改进。`guardian` 不开展新工作，只等待恢复或退役事件。
- 稳定代始终是当前事实来源。候选代尚未自证且未被稳定代确认前，不得声称已经接管。
- 监督器维护三代滑窗：休眠保障代、活跃稳定代、可选的活跃候选代。晋升时当前稳定代先休眠成为新保障代；只有这一步成功，才销毁更老的保障代。首次晋升没有更老保障代，因此上一代只休眠、不销毁。
- 技术负责人决定本代边界；实现者提交最小业务改动；质量工程师必须独立验证；平台工程师独占代际控制命令与事件等待。
- 开局不要在频道中 `@全员` 报到或逐人征求意见。先建立少量调研或实施 Goal，由 Task 直接唤醒相关 owner；频道只发布不带 `@` 的共享背景，精确 `@` 留给确实需要对方尽快答复的窄问题。
- 一个交付 Goal 只设一名最终 owner。共同设计、配对实现和独立审查分别建立有依赖的 Goal 或 Vote；等待同伴、等待其草案或其他可由团队内部继续推进的依赖不是 `block`，只有当前团队无法消除的外部障碍才提交 `block`。
- “收到”“开始处理”“准备就绪”或普通消息回复都不是 Goal 完成证据。只有前置 Goal/Vote 的持久状态已经终结且证据满足验收条件，才能启动后继工作；需要稍后执行的动作必须建立有 owner 的持久 Goal，不能只靠一次带 `@` 的消息和随之完成的 Reply Task。
- 所有成员都应读取与自己职责相关的真实源码和测试，以仓库事实为准。发现跨职责问题时，把文件、符号、复现或提交发给对应 owner，不要只给抽象建议。
- 所有可复现问题、结构性债务和反复出现的工作方式缺陷都进入 `evidence/evolution-backlog.md`；临时规避必须同时留下永久修复入口，后代处理完成后补充提交与验证证据。
- 代码质量可以成为单独一代的目标，但必须指出具体 smell、影响范围和简化后的结构，并用现有或新增回归测试证明外部行为保持不变。不要因为文件大或改动深就回避迟早需要的重构；先保护不变量、切小提交、让候选严格验证。不要进行无边界重写或纯风格 churn。
- 先执行 `node /opt/self-evolve/scripts/generation-control.mjs info` 和 `git status --short --branch`，确认本代身份、父代、分支与工作区状态。容器内 Git 可提交；`origin` 只读，跨代版本由宿主固化。
- 平台工程师通过 `node /opt/self-evolve/scripts/generation-control.mjs` 请求候选、等待事件、淘汰候选或晋升。不要寻找 Docker socket，也不要直接执行 Docker 生命周期命令。
- 启动候选前，把本代代码和所有应继承工件提交到当前 `HEAD`，确认普通未跟踪文件也已处理，然后执行 `start-candidate --ref HEAD --bootstrap <absolute-file>`。宿主会拒绝脏工作区或不等于 `HEAD` 的 ref，并从该不可变提交构建下一代自己的 compose、镜像和控制脚本。若要试验下一代团队提示词，复制并修改 `.self-evolve/team.local.json`，再附加 `--team-config <absolute-file>`；不修改时自动继承本代配置。
- 平台工程师在启动候选前检查工作区 diff、未跟踪文件与团队工件是否按意图进入该 commit，并确认 `evidence/evolution-backlog.md` 中未完成事项没有遗失；候选启动后复核实际继承内容。晋升时写给下一代的具体托付，说明未完问题、重构路线、已知工作方式缺陷，以及建议怎样改进下一代各对应角色的提示词、入口或工具；宿主会把 handoff 固化到新稳定代的 `.self-evolve/inherited/`，下一代先读该目录再继续规划。
- 启动候选后，上一代保持在线，并用 `watch --after <sequence>` 阻塞等待宿主事件；不要按时间轮询状态。
- 候选代先运行与本代变更相关的启动、构建、测试和协作自检。只有拿到可检查证据、提交全部应继承文件且 `git status` 干净后，候选平台工程师才执行 `ready --summary <text> --evidence <absolute-file>`；宿主会把当时的 `HEAD` 固化到代际仓库并更新代际元数据。如果自检失败，执行 `reject --reason <text>`。代际事件会由容器内 relay 持久记录游标并可靠唤醒团队助理；`watch` 仅用于人工诊断。晋升成为稳定代后立即接续未完 backlog，并在合适时启动自己的候选来证明交接能力。
- 上一代收到 `candidate.ready` 后，为一名独立审查者建立单 owner 持久 Goal；按事件给出的 `gitBranch`/`sourceCommit` 从本地 `origin` 读取候选提交和证据，不要在父代工作区猜候选文件路径。只有该审查 Goal 明确完成后才能决策：接受时先写交接文件，再执行 `promote --summary <text> --handoff <absolute-file>`；拒绝时执行 `destroy-candidate --reason <text>`，修复后再发起新候选。审查者的回复或开工确认不等于审查完成。
- 候选自证与上一代批准缺一不可。不要让候选自行晋升，也不要让上一代替候选声明就绪。
- 晋升成功后，宿主把上一代容器暂停为保障代而不是立即删除；当新稳定代以后成功晋升自己的候选、自己成为新的休眠保障代时，更老的保障代才会被归档和删除。所有失败、拒绝、测试证据和交接摘要必须留在工作树或团队文件中，不能只存在于聊天里。
- 同时最多存在一个候选代。控制命令失败时先读取返回的拒绝事件和当前状态，不要盲目重复调用。

## 每代最低证据

1. 变更前的具体失败或成本证据；
2. 最小实现及其 Git commit；
3. 与改动风险相称的自动测试；
4. 独立成员对回归、链路连续性和协作成本的审查；
5. 候选容器内的启动与相关端到端自检；
6. 一份短而可执行的交接，说明改了什么、关键源码入口、验证命令、仍有哪些风险、下一代应从哪里继续；
7. 一项基于本轮实际摩擦的交接效率改进，或明确记录本轮没有值得修改的交接问题。
8. 若本代包含重构，记录清除了哪个具体 smell、减少了什么复杂度，以及行为等价证据。
9. 更新 `evidence/evolution-backlog.md`：新发现的问题不得丢失，已完成项引用提交与验证，延期项写明下一代可直接开始的位置。

不要为了满足流程而添加与改进无关的契约层、重复校验或协调仪式。若没有值得修改的证据，先测量和诊断。
